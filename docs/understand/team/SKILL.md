# understand-html — 코드를 단계별로 이해하고 HTML로 남기기

처음 보는 코드를 **적은 에너지로, 개발 용어 없이, 업무 관점으로** 이해하고, 이해한 내용을 브라우저로 바로 열리는 **HTML 파일**로 남긴다.
목적은 나중의 **코드 리뷰와 인수인계를 편하게** 하는 것이다.

> 이 스킬은 팀원 4명(SangwooSong의 `understand-project`, KewryByun의 `easy-understand`, ctkim1005의 `html-report`, sy9169의 `code-explainer-html`)의 스킬을 비교해 합친 것이다.

## 대상 독자 가정
- 코드를 처음 본다. 이해에 쓸 수 있는 에너지가 적다.
- 클래스·트랜잭션 같은 개발 용어보다 **누가 / 무엇을 / 왜 / 어떤 규칙으로**를 먼저 알고 싶다.
- 나중에 PR을 리뷰해야 하므로 "무엇을 확인해야 하는지"가 필요하다.

## 진행 순서

### 0. 코드 파악 (사용자에게 설명하지 않는다)
- 읽는 순서: 빌드 파일 → 설정 → 진입점 → 화면/요청 목록 → 업무 규칙(서비스) → 핵심 계산 → 데이터 → 테스트.
- **테스트는 규칙의 가장 짧은 설명서다.** 숫자 예시는 테스트와 기본값에서 가져온다.
- **상태 변경·삭제 같은 동작은 서비스 코드를 직접 읽고 확인한다.** 상태 목록(enum)만 보고 단정하지 않는다. (예: 상태에 "취소"가 있어도 실제로는 주문을 지울 수 있다.)
- 기획 설명이나 안내 자료가 있으면 코드와 **비교**한다. 다른 점은 사실처럼 쓰지 말고 "확인이 필요한 점"으로 남긴다.
- `.ua/knowledge-graph.json`이 있고 최신이면 방향을 잡는 용도로만 쓴다. 최신 여부는 그래프의 `project.gitCommitHash`와 `git rev-parse HEAD`를 비교하고 `git diff --name-only <hash> HEAD -- .`가 비었는지 본다. **설명에 넣는 사실은 소스에서 다시 확인한다**(요약은 추정일 수 있다).
- 사용자가 "이해만 해봐"라고 하면 설명 없이 "파악했다, 다음 지시를 달라"고만 답한다.
- 읽지 않은 파일은 읽지 않았다고 말한다.

### 1. 브레인스토밍 (짧게, 한 번)
- 사용자 배경(처음 보는지, 쓸 수 있는 에너지, 목적)을 확인한다.
- 이해 경로를 표로 제안하고 **추천안 하나**를 밝힌다. 가장 어려운 단계는 뒤로 미룬다.

| 단계 | 볼 것 | 목표 |
| --- | --- | --- |
| 1. 업무 이해 | 용어, 기본 규칙, 등장하는 것들 | 앱이 푸는 문제를 한 문단으로 말할 수 있음 |
| 2. 사용자 흐름 | 로그인부터 주요 작업까지 | 사용자 관점 시나리오 |
| 3. 핵심 규칙 | 가장 복잡한 계산·규칙 | 리뷰에서 가장 위험한 곳 |
| 4. 리뷰 포인트 | 동시성, 삭제, 권한, 성능 | 체크리스트 |

- 산출물 종류와 설명 깊이는 **한 번만** 묻는다. 이미 답했다면 다시 묻지 않는다.
- 의심스러운 부분은 "검증 전 후보"로 따로 적고 사실처럼 말하지 않는다.

### 2. 단계별 대화 (한 응답에 한 단계)
- 사용자가 "다음", "N단계 진행"이라고 할 때만 넘어간다.
- 개발 용어 대신 비유를 쓴다. 예: 접수 창구(요청 받기) / 담당자(업무 규칙) / 계산 전문가(핵심 계산) / 장부(저장).
- 구성: 한 문단 요약 → 표나 짧은 목록 → **확인 질문 1~2개**("현실과 다른 점이 없나요?").
- 사용자의 답은 이후 설명과 문서에 반영한다. 이미 정해진 결정을 다시 따지지 않는다.

### 3. HTML 작성·누적
- 단계마다(또는 "문서에 추가해줘" 요청 시) **같은 파일을 수정**한다. 새 파일을 만들지 않는다. 기존 파일은 부분 수정하고, 새로 알게 된 사실과 어긋난 문구는 함께 고친다.
- 템플릿에서 시작할 때 `{{...}}` 자리를 모두 채우거나 지운다.
- **문자열 치환으로 파일을 만들 때** `/* ... */` 같은 주석이나 괄호를 통째로 지우거나 닫는 부분을 빠뜨리지 않는다. (주석이 안 닫히면 그 아래 함수가 전부 사라지는데 문법 검사는 통과한다.)

### 4. 검증 (필수. "열어 봤다"로 대체하지 않는다)
아래 "검증 방법"을 실행하고 결과를 확인한다. 직접 눌러 보지 못한 부분은 보고에 그대로 적는다.

### 5. 마무리 보고
- 만든 파일 경로, 단순화한 부분, 검증 결과(통과 항목)를 알려 준다.
- **브라우저에서 실제로 동작을 확인했는지** 명시한다. 못 했다면 "작성만 했다"고 쓴다.
- 커밋·푸시·PR은 사용자가 정한다. 임의로 하지 않는다. 다음 단계를 제안하고 진행 여부를 묻는다.

## 공통 작성 원칙
- **사실만 쓴다.** 코드·테스트에서 확인한 것만 단정한다. 추정은 "추정"으로 표시하고, 모르면 "확인 필요" 또는 "소스에서 확인되지 않음"이라고 쓴다. 코드에 없는 기능을 만들어 넣지 않는다.
- **업무 언어 먼저.** 개발 용어(클래스, DB, API, 프레임워크, 트랜잭션 등)는 쓰지 않고 일상어로 풀어 쓴다. 코드 이름이 필요한 곳은 접이식 "코드 리뷰용" 영역에만 둔다.
- **숫자는 코드와 일치한다.** 기본값·예시·계산식·오류 메시지는 실제 코드와 테스트에서 가져온다. 단순화했다면 화면에 그렇게 적는다. 숫자의 출처(초기값)를 밝히고, 값이 바뀌면 달라질 수 있다고 적는다.
- **파생 수치(일수·비용 등)는 손으로 적지 않는다.** 계산 함수로 만들어 화면의 다른 값과 어긋나지 않게 한다.
- **"확인이 필요한 점" 카드**를 눈에 띄게(경고색 테두리) 둔다. 코드에서 읽은 사실이며 확정된 요구사항이 아님을 적고, 결론이 나오면 갱신한다.
- 직접 실행해 확인하지 못한 동작은 "실행해서 확인하지 못했다"고 적는다.

## HTML 공통 규칙
- **단일 파일.** CSS와 JS는 인라인. **외부 CDN·폰트·이미지·프레임워크 링크 금지**(사내망·오프라인에서 더블클릭으로 열려야 한다).
- 색은 `:root` 변수로 정의하고 라이트/다크(`prefers-color-scheme`)를 모두 지원한다. 색만으로 정보를 구분하지 않는다(텍스트·아이콘 병기).
- 모바일 폭(390px)에서도 깨지지 않게 한다. 표가 넓으면 표만 가로 스크롤되게 감싸고, 페이지 전체가 가로 스크롤되면 안 된다.
- 키보드 포커스가 보여야 한다. 탭은 `role="tab"`, 좌우 방향키 지원.
- `localStorage`는 항상 try/catch로 감싼다(없어도 화면이 정상이어야 한다).
- `<title>`은 2~4단어. 한국어로 쓴다.
- 사내 코드 설명이므로 외부(claude.ai Artifact 등)에 게시하지 않는다. 필요하면 사용자 확인을 먼저 받는다.

## A. 이해 가이드 규칙 (탭 3개)
탭은 이해 순서대로 3개이며 개수를 바꾸려면 먼저 묻는다. 4단계 이후 내용은 마지막 탭에 카드로 추가한다.

1. **무엇을 하는 시스템인가요?** — 누가 쓰고, 어떤 문제를 풀고, 큰 흐름은 무엇인지. 용어와 기본값을 눌러 보며 익힌다(클릭하면 설명이 바뀌는 흐름·목록).
2. **어떤 규칙으로 계산·판단하나요?** — 핵심 업무 규칙. **입력을 바꾸면 결과가 바뀌는 슬라이더·계산기 체험 필수.** 규칙을 실제 숫자 예시와 함께 보여 준다.
3. **일이 어떻게 진행·관리되나요?** — 상태 변화, 허용/불허 전환(버튼으로 체험), 동시에 바꿀 때의 처리, 실패하는 시나리오, **확인이 필요한 점** 카드, 이해 확인 퀴즈.

- **카드마다 인터랙션 하나 이상:** 선택해서 보기, 입력해서 계산, 슬라이더, 상태 체험, 시나리오 "다음 ▶"(실패 시나리오는 이유와 함께 멈춤), 퀴즈.
- 각 탭 끝에 "한 줄 요약" 박스를 두고, 단계 이동(이전/다음)과 키보드 ←/→를 지원한다.
- 코드 리뷰용 "업무 규칙 ↔ 담당 파일" 표는 `<details>` 접이식으로 따로 둔다.

## B. 프로토타입 규칙
- **Mock Data는 화면을 열자마자 보여야 한다.** 코드의 초기값(기본 기준값)을 따르고, 서로 다른 상태의 가짜 데이터 2건 이상을 미리 넣는다.
- 가짜 데이터는 프로토타입의 계산 함수로 만들어 화면의 다른 값과 어긋나지 않게 한다.
- 실제 앱의 핵심 흐름을 한 파일에서 재현한다: 목록 → 새로 만들기(시뮬레이션) → 확정 → 상태 변경 → 기준 데이터 수정.
- 코드의 입력 제한(총량 상한, 개수 범위 등)도 같이 검사한다.
- 서버·DB 없이 메모리로만 동작한다(새로고침하면 초기화). 계산은 실제 로직을 **단순화**한 것이므로 결과가 실제와 다를 수 있다고 화면에 명시한다.

## C. 구조 리포트 규칙 (개발자·리뷰어용)
처음 보는 사람이 5분 안에 "무엇을 하고 어떻게 돌아가는지" 파악하도록 한 파일로 정리한다. 이 산출물에서만 개발 용어와 코드 식별자(`code`)를 쓸 수 있다.

- 섹션 순서: 헤더(이름·한 줄 설명·생성일) → 개요(문제와 주요 사용자) → 업무 흐름 → 주요 기능 → 화면·요청 흐름 표 → 핵심 규칙과 숫자 예시 → 기본 데이터 표(화면의 값과 일치) → 코드 구조(계층 그림) → 알아둘 점 → 리뷰 체크 포인트 → 관련 파일 맵. 해당 없는 섹션은 통째로 지운다.
- 목차는 상단에 두고 섹션 제목에 `id`를 붙여 앵커로 연결한다.
- 그림은 실제 구조·흐름을 보여 줄 때만(인라인 SVG). 이모지와 장식용 이미지는 쓰지 않는다.
- 코드 전체를 붙여 넣지 않는다. 규칙은 주석과 테스트를 근거로 요약한다.
- 모듈 하나를 설명할 때는 입력과 출력, 계산 순서, 숫자 예시(테스트 값), 스스로 점검하는 장치, 알아둘 점(미사용 기능 등 확인한 사실만), 리뷰 체크리스트를 담는다.

## 검증 방법
1. **스크립트 오류 없음.** 화면 없이 브라우저를 띄우거나(Edge/Chrome headless + DevTools) jsdom으로 파일을 열어 콘솔 예외가 0건인지 본다.
2. **동작 확인.** 탭 전환·방향키, 슬라이더·계산기·상태 버튼이 반응하는가. Mock 데이터가 실제로 보이는가(계산 함수만 따로 돌려 보고 끝내지 않는다).
3. **값 일치.** 계산기·예시가 코드의 테스트 값과 같은 결과를 내는가(예: 테스트의 기대 숫자). `NaN`/`undefined`가 화면에 없는가.
4. **화면 확인.** 가능하면 스크린샷으로 모바일 폭과 다크 모드에서 깨지지 않는지 본다.
5. 화면 id나 버튼 문구를 바꿨다면 검증 스크립트의 선택자도 함께 맞춘다. `scripts/verify.js`는 KewryByun의 가이드·프로토타입 템플릿의 화면 id에 맞춰져 있으므로, `guide-template.html`(sy9169 계열)로 만든 가이드에 쓰려면 선택자를 맞춰야 한다.

jsdom을 쓸 때: 프로젝트나 홈 폴더(`~`)가 아니라 **임시 폴더**에 설치한다(홈에 `package.json`이 있으면 의존성이 섞인다). Node 20 계열은 최신 jsdom과 맞지 않으므로 `jsdom@24`를 쓴다.
```
mkdir <임시폴더> && cd <임시폴더> && npm init -y && npm i jsdom@24
node <스킬폴더>/scripts/verify.js <HTML 파일들>
```
`verify.js`는 현재 폴더에서 jsdom을 찾으므로 jsdom을 설치한 폴더에서 실행한다.

- 코드를 읽지 않고 추측이나 일반론으로 채우지 않는다.
- 코드를 수정하거나 리팩터링을 제안하지 않는다. 이 스킬은 **읽기와 문서화**만 한다. 버그·보안 리뷰는 `/code-review`를 쓴다.
- 검증하지 않은 의견을 확정 사실처럼 쓰지 않는다. 섹션 제목만 있고 내용이 "TBD"인 빈 섹션을 남기지 않는다.
- 외부 CSS 프레임워크나 CDN을 링크하지 않는다.
