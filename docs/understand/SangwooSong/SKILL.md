# 프로젝트 이해 가이드 (브레인스토밍 → 단계별 대화 → basic_guide.html)

## 목적
- 사용자는 코드를 처음 보며, 이해에 많은 에너지를 쓸 수 없다.
- 단계별로 이해해 두어 **나중의 코드 리뷰가 편해지게** 한다.
- 개발 지식 없이 **요구사항(업무) 위주**로 설명한다.

## 진행 순서

### 0. 코드 파악 (사용자에게 설명하지 않는다)
- 먼저 코드를 읽는다: 빌드 파일, 설정, 진입점, 컨트롤러/라우트, 서비스, 핵심 로직, 화면 템플릿, 테스트.
- 사용자가 "이해만 해봐"라고 하면 설명 없이 읽고 "파악했다, 다음 지시를 달라"고만 답한다.
- 이후 모든 설명은 **읽은 코드에서 확인한 사실**만 쓴다. 읽지 않은 파일은 읽지 않았다고 말한다.

### 1. 브레인스토밍 (먼저, 짧게)
- 사용자 배경을 확인한다: 코드 첫 접촉, 에너지 제한, 목적(리뷰 대비).
- 이해 경로를 표로 제안하고 **추천안 하나**를 밝힌다. 기본 경로:

| 단계 | 볼 것 | 목표 |
|---|---|---|
| 1. 업무 이해 | 도메인 규칙, 등장하는 것들(공장·배 등) | 앱이 풀려는 문제를 한 문단으로 말할 수 있음 |
| 2. 화면/사용자 흐름 | 로그인부터 주요 작업까지 | 사용자 관점 시나리오 |
| 3. 요청 한 건 추적 | 버튼 하나가 거치는 길 (비유 사용) | 역할 분담과 데이터 흐름 |
| 4. 핵심 로직 | 가장 복잡한 계산/규칙 | 리뷰에서 가장 위험한 부분 |
| 5. 리뷰 포인트 | 동시성, 삭제, 권한, 성능 등 | 체크리스트 |

- 가장 어려운 단계는 마지막으로 미룬다.
- 산출물 형태(대화로 한 단계씩 / 문서 한 번에 / 대화+요약 누적)와 설명 깊이를 사용자에게 **한 번만** 묻는다. 이미 답했다면 다시 묻지 않는다.
- 코드를 읽다 의심스러웠던 부분은 "검증 전 후보"로 따로 적어 두고, 사실처럼 말하지 않는다.

### 2. 단계별 대화 (한 번에 한 단계)
- 한 응답에는 **한 단계만** 다룬다. 사용자가 "다음"/"N단계 진행"이라고 하면 넘어간다.
- 개발 용어(클래스, 컨트롤러, 트랜잭션 등)를 쓰지 않는다. 필요하면 비유로 바꾼다.
  - 예: 접수 창구(요청 받기) / 담당자(업무 규칙) / 계산 전문가(핵심 계산) / 장부(저장)
- 구성: 한 문단 요약 → 표나 짧은 목록 → **확인 질문 1~2개**(현실과 다른 점이 없는지).
- 코드에서 요구사항과 어긋나 보이는 동작을 발견하면 사실로 단정하지 말고 **"확인이 필요한 점"**으로 질문한다. (예: 취소하면 주문이 삭제되는데 취소 필터가 있음)
- 사용자의 답을 받으면 이후 설명과 문서에 반영한다. 이미 정해진 결정을 다시 따지지 않는다.

### 3. basic_guide.html에 누적
사용자가 요청한 단계마다(또는 "문서에 추가해줘" 요청 시) 같은 파일에 내용을 **추가·수정**한다. 새 파일을 만들지 않는다.

**파일 위치:** `docs/understand/<작성자>/basic_guide.html` (이 SKILL.md와 같은 폴더)

**구성 규칙**
- 단일 HTML 파일(외부 라이브러리 없음, 인라인 CSS/JS), 한국어.
- **탭은 3개** (사용자가 지정한 개수를 유지): 업무 이해 / 사용자 흐름 / 핵심 동작. 4~5단계가 생기면 새 탭을 만들지 말고 마지막 탭에 카드로 추가하고, 탭 수를 바꾸려면 먼저 묻는다.
- 개발 지식 없이 읽히는 내용만 본문에 둔다. 코드 리뷰용 파일 매핑은 `<details>` 접이식으로 따로 둔다.
- **카드마다 인터랙션 하나 이상**: 클릭해서 보기, 입력해서 계산하기, 슬라이더, 상태 전이 체험, 시나리오 선택 후 "다음 ▶"(실패 시나리오는 해당 단계에서 이유와 함께 멈춤), 퀴즈.
- 인터랙션의 규칙·숫자는 **실제 코드와 일치**해야 한다. 개념 이해용으로 단순화했다면 화면에 그렇게 명시한다.
- 기본 마스터 값 등 숫자의 출처(초기값)를 밝히고, 값이 바뀌면 문서와 달라질 수 있다고 적는다.
- "확인이 필요한 점" 카드는 눈에 띄게(경고색 테두리) 두고, 코드에서 읽은 사실이며 확정된 요구사항이 아님을 적는다. 결론이 나오면 카드를 갱신한다.
- 스타일: `:root` 색상 토큰, 다크 모드(`prefers-color-scheme`), 모바일 폭 대응, 키보드 포커스 표시, 탭은 `role="tab"`과 좌우 방향키 지원.
- `localStorage`(마지막 탭 기억 등)는 반드시 try/catch로 감싼다.

**수정 방식**
- 기존 파일은 Edit로 부분 수정한다. 전체를 다시 쓰지 않는다.
- 이전에 쓴 문구가 새로 알게 된 사실과 어긋나면 함께 고친다.

### 4. 마무리 보고
- 무엇을 추가했는지 짧게 요약한다.
- **브라우저에서 실제로 열어 보지 않았다면 "작성만 했고 동작은 확인하지 못했다"고 명시**한다.
- 문서 폴더를 gitignore에 넣을지, 커밋할지는 사용자가 정한다. 임의로 커밋하지 않는다.
- 다음 단계를 제안하고 진행 여부를 묻는다.

## 하지 않는 것
- 한 번에 여러 단계를 몰아서 설명하지 않는다.
- 코드를 읽지 않고 추측으로 설명하지 않는다.
- 사용자가 묻지 않은 리팩터링·코드 수정을 하지 않는다. 이 스킬은 **읽기와 문서화**만 한다.
- 검증하지 않은 리뷰 의견을 확정 사실처럼 쓰지 않는다.

## 참고 예시
이 폴더의 `basic_guide.html`은 배터리 해상 운송 앱을 대상으로 만든 결과물이다. 탭 구성(업무 이해 / 사용자 흐름 / 주문과 3가지 안), 인터랙션 종류, "확인이 필요한 점" 카드 형식을 참고한다.
