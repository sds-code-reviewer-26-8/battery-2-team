# code-explainer-html

처음 보는 코드를 **적은 에너지로 단계별로 이해**하고, 나중의 **코드 리뷰를 편하게** 하기 위한 스킬이다.
이해한 내용은 서버나 빌드 없이 브라우저로 바로 열리는 **단일 HTML 파일**로 남긴다.

## 산출물 두 가지

| 모드 | 파일 | 언제 | 템플릿 |
| --- | --- | --- | --- |
| **가이드형 (기본)** | `basic_guide.html` | 프로젝트 전체를 비개발 언어로 이해하고 싶을 때. 탭 3개 + 인터랙션 | `assets/guide-template.html` |
| 보고서형 | `<대상>-explained.html` | 모듈 하나(예: 핵심 계산 로직)를 깊게 설명할 때. 한 페이지 | `assets/report-template.html` |

저장 위치: `docs/understand/<작성자>/` (이 SKILL.md와 같은 폴더).

## 대상 독자 가정
- 코드를 처음 본다. 이해에 쓸 에너지가 적다.
- 클래스·트랜잭션 같은 개발 용어보다 **업무 의미**를 먼저 알고 싶다.
- 나중에 PR을 리뷰해야 하므로 "무엇을 확인해야 하는지"가 필요하다.

## 진행 순서

### 0. 코드 파악 (사용자에게 설명하지 않는다)
- 빌드 파일, 설정, 진입점, 컨트롤러, 서비스, 핵심 로직, 화면, 테스트 순으로 읽는다.
- 테스트는 규칙의 가장 짧은 설명서다. 숫자 예시는 테스트와 기본값에서 가져온다.
- `.ua/knowledge-graph.json`이 있고 최신이면 방향을 잡는 용도로만 쓴다. 최신 여부는 그래프의 `project.gitCommitHash`와 `git rev-parse HEAD`를 비교하고 `git diff --name-only <hash> HEAD -- .`가 비었는지 본다. **설명에 넣는 사실은 소스에서 다시 확인한다**(요약은 추정일 수 있다).
- 사용자가 "이해만 해봐"라고 하면 설명 없이 "파악했다, 다음 지시를 달라"고만 답한다.
- 읽지 않은 파일은 읽지 않았다고 말한다.

### 1. 브레인스토밍 (짧게, 한 번)
- 사용자 배경(처음 보는지, 쓸 수 있는 에너지, 목적)을 확인한다.
- 이해 경로를 표로 제안하고 **추천안 하나**를 밝힌다.

| 단계 | 볼 것 | 목표 |
| --- | --- | --- |
| 1. 업무 이해 | 용어, 기본 규칙 | 앱이 푸는 문제를 한 문단으로 말할 수 있음 |
| 2. 사용자 흐름 | 로그인부터 주요 작업까지 | 사용자 관점 시나리오 |
| 3. 핵심 동작 | 가장 복잡한 계산·규칙 | 리뷰에서 가장 위험한 곳 |
| 4. 리뷰 포인트 | 동시성, 삭제, 권한, 성능 | 체크리스트 |

- 가장 어려운 단계는 뒤로 미룬다.
- 산출물 형태와 설명 깊이는 **한 번만** 묻는다. 이미 답했다면 다시 묻지 않는다.
- 코드를 읽다 의심스러운 부분은 "검증 전 후보"로 따로 적고 사실처럼 말하지 않는다.

### 2. 단계별 대화 (한 응답에 한 단계)
- 사용자가 "다음", "N단계 진행"이라고 할 때만 넘어간다.
- 개발 용어 대신 비유를 쓴다. 예: 접수 창구(요청 받기) / 담당자(업무 규칙) / 계산 전문가(핵심 계산) / 장부(저장).
- 구성: 한 문단 요약 → 표나 짧은 목록 → 확인 질문 1~2개("현실과 다른 점이 없나요?").
- 요구사항과 어긋나 보이는 동작은 단정하지 말고 **"확인이 필요한 점"**으로 질문한다.
- 사용자의 답은 이후 설명과 문서에 반영한다. 이미 정해진 결정을 다시 따지지 않는다.

### 3. HTML에 누적
단계마다(또는 "문서에 추가해줘" 요청 시) **같은 파일을 수정**한다. 새 파일을 만들지 않는다. 기존 파일은 Edit로 부분 수정하고, 새로 알게 된 사실과 어긋난 문구는 함께 고친다.

**가이드형 규칙**
- 템플릿 `assets/guide-template.html`을 복사해 시작한다. `{{...}}`를 모두 채우거나 지운다.
- 탭은 3개를 유지한다(바꾸려면 먼저 묻는다). 4단계 이후 내용은 마지막 탭에 카드로 추가한다.
- 본문은 개발 지식 없이 읽혀야 한다. 코드 리뷰용 "업무 규칙 ↔ 담당 파일" 표는 `<details>` 접이식으로 따로 둔다.
- **카드마다 인터랙션 하나 이상**: 선택해서 보기, 입력해서 계산, 슬라이더, 상태 체험, 시나리오 "다음 ▶"(실패 시나리오는 이유와 함께 멈춤), 퀴즈.
- 인터랙션의 규칙·숫자·오류 메시지는 **실제 코드와 일치**해야 한다. 단순화했다면 화면에 적는다.
- 숫자의 출처(초기값)를 밝히고, 값이 바뀌면 달라질 수 있다고 적는다.
- **"확인이 필요한 점" 카드**(`.card.warn`)를 둔다. 코드에서 읽은 사실이며 확정된 요구사항이 아님을 적고, 결론이 나오면 갱신한다.
- 직접 실행해 보지 못한 동작은 카드에 "실행해서 확인하지 못했다"고 적는다.

**보고서형 규칙**
- `assets/report-template.html`을 복사한다. 섹션: 무엇을 하는 코드 → 흐름 → 규칙과 숫자 예시 → 입출력(SVG) → 알아둘 점 → 리뷰 체크 → 관련 파일.
- 그림은 실제 구조나 흐름을 보여 줄 때만 쓴다.

### 4. 마무리 보고
- 추가한 내용을 짧게 요약한다.
- **브라우저에서 실제로 열어 동작을 확인했는지** 명시한다. 확인하지 못했다면 "작성만 했다"고 쓴다.
- 커밋·푸시·PR은 사용자가 정한다. 임의로 하지 않는다.
- 다음 단계를 제안하고 진행 여부를 묻는다.

## HTML 공통 규칙
- 단일 파일, 한국어. **외부 CDN·폰트·이미지 금지**(오프라인에서도 열려야 한다). CSS/JS는 인라인.
- 색은 `:root` 변수로 정의하고 라이트/다크 모두 지원한다(템플릿에 구현됨).
- 모바일 폭에서 가로 스크롤이 생기지 않게 한다. 키보드 포커스가 보여야 한다.
- 탭은 `role="tab"`, 좌우 방향키 지원. `localStorage`는 항상 try/catch.
- `<title>`은 2~4단어.
- 사내 코드 설명이므로 외부(claude.ai Artifact 등)에 게시하지 않는다. 필요하면 사용자 확인을 먼저 받는다.

## 검증 방법 (권장)
브라우저를 화면 없이 띄워 파일을 열고 확인한다.
1. 스크립트 오류가 없는가 (콘솔 예외 0건)
2. 탭 전환·방향키가 되는가
3. 계산기·게이지·상태 체험이 **코드의 테스트 값과 같은 결과**를 내는가
4. 모바일 폭과 다크 모드에서 깨지지 않는가

## 하지 않는 것
- 한 번에 여러 단계를 몰아서 설명하지 않는다.
- 코드를 읽지 않고 추측으로 설명하지 않는다.
- 코드를 수정하거나 리팩터링을 제안하지 않는다. 이 스킬은 **읽기와 문서화**만 한다.
- 검증하지 않은 리뷰 의견을 확정 사실처럼 쓰지 않는다. 버그·보안 리뷰는 `/code-review`를 쓴다.

## 사용 방법
이 폴더의 `SKILL.md`와 `assets/`를 `.claude/skills/code-explainer-html/`에 복사하면 `/code-explainer-html`로 쓸 수 있다.
(`.claude/`는 저장소에서 gitignore 대상이라 원본을 `docs/understand/`에 둔다.)

## 참고 예시
- `basic_guide.html`: 배터리 주문 앱을 대상으로 만든 가이드형 결과물 (탭 3개, 여러 종류의 인터랙션, 확인이 필요한 점 카드, 퀴즈).
- `planner-explained.html`: 경로 계산(Planner) 하나를 설명한 보고서형 결과물.
- `project-overview.html`: 프로젝트 전체를 한 페이지로 정리한 보고서형 결과물.
