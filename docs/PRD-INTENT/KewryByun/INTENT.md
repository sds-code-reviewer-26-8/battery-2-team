## 1. 목적

- 담당자가 **"몇 개를 어디서 주문하면, 배를 어떻게 돌리는 게 좋은가"**를 손으로 계산하지 않고 비교해서 결정하게 한다. **[문서]**
- 결정은 사람이 한다. 시스템은 근거(3가지 안과 비용·일정)를 제공하고, 선택된 안을 **기록으로 고정**한다. **[코드]**
- 이 프로젝트는 팀 과제의 Legacy 앱이며, 이후 **유지보수·기능 추가·리팩토링을 안전하게 하기 위한 구현-검증 Loop**의 대상이다. 따라서 "고치기 쉬움"보다 **"고쳐도 깨지지 않았음을 확인할 수 있음"**이 중요하다. **[문서]**

## 2. 설계 의도

### 2.1 계산 로직과 저장 로직을 분리했다
- `simulation/`(Planner·Plan·Master)은 JPA·Spring과 무관한 **순수 계산**이다. DB 없이 단위 테스트가 가능하다. **[코드]**
- 의도: 가장 복잡하고 바뀌기 쉬운 규칙을 격리해 빠르게 검증하려는 것. **[추정]**
- **지킬 것**: `Planner`에 DB·세션·화면 의존을 넣지 않는다. 기준 값은 `Master` 스냅샷으로만 받는다.

### 2.2 서버가 다시 계산한다 (클라이언트를 믿지 않는다)
- 확정 요청이 와도 서버가 같은 입력으로 `simulate`를 다시 돌려 계획을 만든다. 화면이 보여 준 숫자를 그대로 저장하지 않는다. **[코드]**
- 의도: 화면 조작·오래된 화면으로 잘못된 금액·일정이 저장되는 것을 막는다. **[추정]**
- **지킬 것**: 금액·일정은 서버 계산값만 저장한다. 브라우저 JS는 표시 전용으로 둔다.

### 2.3 두 종류의 낙관적 충돌 감지
- 확정: **기준 정보 버전** — 시뮬레이션 이후 기준 정보가 바뀌었으면 거부. 상태 변경: **주문 버전** — 화면에서 본 뒤 다른 사람이 바꿨으면 거부. **[코드]**
- 의도: 잠금 없이 동시 작업을 허용하되, 오래된 정보로 확정·변경되는 것만 막는다. **[추정]**
- **지킬 것**: 새 쓰기 기능에도 "사용자가 본 버전"을 함께 받아 비교한다. 충돌은 API 409 / 화면 안내 메시지로 일반 오류와 구분한다.

### 2.4 확정 주문은 당시의 기준으로 굳힌다
- 주문에는 계획과 함께 **계산에 쓴 기준 정보 스냅샷**이 저장된다. 이후 기준 정보를 바꿔도 기존 주문은 변하지 않는다. **[코드]**
- 의도: 계약·실행이 시작된 주문의 비용·일정이 사후에 흔들리지 않게 한다. **[추정]**
- **지킬 것**: 기준 정보 수정이 과거 주문을 재계산하게 만들지 않는다. 저장 형식(`StoredPlan`)을 바꿀 때는 기존 데이터 호환을 먼저 정한다.

### 2.5 경로안을 하나가 아니라 3가지로 보여 준다
- COST/FAST는 배 배정·왕복 구성의 가능한 경우를 모두 따져 최소값을 고르고(완전 탐색), NEAR는 "가까운 곳부터"라는 단순 규칙이다. **[코드]**
- 의도: 비용·속도·단순함은 서로 트레이드오프라 하나의 정답을 강요하지 않는다. **[추정]**
- **지킬 것**: 3안의 키(`COST/FAST/NEAR`)는 API·저장 데이터가 쓰므로 이름을 바꾸면 영향이 크다.
- **주의**: 완전 탐색이라 공장 수·배 수가 늘면 조합이 급증한다. 현재는 공장 4곳·배 최대 4척이라 감당 가능하다. **[추정]**

### 2.6 "한국 대기 무료"가 경로 계산의 핵심 규칙이다
- 주문이 재고 상한을 넘으면 같은 나라를 여러 번 가야 하고, 한국에 돌아와 쉬는 시간은 비용이 없으므로 **늦게 출항해 재고를 채운 뒤 가는 것**이 이득이다. **[문서·코드]**
- **지킬 것**: 운항비는 "정박 제외 항해 일수"만 센다. 이 규칙을 바꾸면 3안 모두 결과가 달라지므로 PRD BR-06·07과 `PlannerTest`를 함께 고친다.

### 2.7 입력 검증은 "전부 모아서, 하나도 저장하지 않는다"
- 기준 정보 수정은 오류를 모두 모은 뒤 한 번에 알리고, 하나라도 틀리면 저장하지 않는다. **[코드]**
- 의도: 일부만 저장돼 계산이 어긋난 기준 정보가 생기지 않게 한다. **[추정]**

### 2.8 단위 규칙
- 수량은 K(1,000개), 금액 저장은 원, 화면 입력은 억 원. **[코드]** 변환은 경계(입력·저장·표시)에서만 한다.
- **지킬 것**: 새 비용 항목(예: 공장 운영비)도 같은 규칙으로 저장하고, 원 단위로 떨어지지 않는 값은 거부한다.

## 3. 변경 시 지켜야 할 방향 (가드레일)

1. **규칙을 바꿀 때는 PRD와 테스트를 같이 바꾼다.** 특히 BR-01~10의 근거는 `PlannerTest`다.
2. **계산은 서버, 화면은 표시.** 확정 시 서버 재계산을 우회하는 경로를 만들지 않는다.
3. **충돌 감지(버전)를 약화시키지 않는다.** 새 쓰기 기능에는 같은 방식의 버전 검사를 붙인다.
4. **확정된 주문은 불변에 가깝게 다룬다.** 사후 재계산·덮어쓰기를 하지 않는다.
5. **전부 저장하거나 아무것도 저장하지 않는다.** 부분 저장을 만드는 변경을 경계한다.
6. **변경마다 `./gradlew test`로 확인한다.** 버그를 고칠 때는 그 버그를 재현하는 테스트를 먼저 추가한다.
7. **사용자가 이유를 알 수 있게 거부한다.** UI·메시지는 한국어이고, 예외 상황(없는 주문 등)도 오류 화면이 아니라 안내 메시지로 처리한다.

## 4. 의도적으로 하지 않은 것 (현재 범위 밖)

- 다계정·권한: 로그인은 데모용 단일 계정이다(`AppController`에 하드코딩). **[코드]**
- 고객사·납기·공장 운영비: PPT에 "추가개발 필요"로 표시된 항목. **[문서]**
- 선박 적재량 제한: PPT는 "컨테이너 적재량은 충분"하다고 가정한다. **[문서]**
- 공장별 물량 자동 배분: 담당자가 입력한 배분량을 그대로 계산한다(§6-2 참고). **[코드]**

## 5. 확장 시 고려점

기존 주문 데이터 호환이 공통 과제다.
- **납기 반영**: 경로 후보의 총 소요일을 납기와 비교한다. 새 입력은 null 허용으로 시작해 기존 주문을 깨지 않는다.
- **공장 운영비**: 기준 정보에 항목을 추가하고 BR-07의 비용식을 확장한다. 기존 주문 스냅샷에 새 필드가 없어도 읽혀야 한다.

## 6. 열린 질문 / 확인된 불일치 (팀 합의 필요)

### 6-1. 취소 동작 — PPT와 코드가 다르고, 화면에서 오류가 난다
- **PPT**: "취소: 어떤 사정으로 취소된 상태". 목록에서 상태로 구분되고, 상태 필터에도 "취소"가 있다.
- **코드**: `BatteryService.changeStatus`는 상태를 `CANCELED`로 바꾼 뒤 **주문 자체를 삭제**한다. 변경 이력(확정·취소 2건)만 남는다.
- **실제 동작(테스트로 확인)**: 취소 요청 → 302로 `/orders/{id}`로 이동 → 주문이 없어 `BusinessException`("주문을 찾을 수 없습니다")이 발생하고, 컨트롤러에 예외 처리기가 없어 **오류 화면**이 된다. 주문 목록에서 "취소" 건수는 항상 0이다. (임시 테스트로 확인 후 삭제함)
- **제안**: 취소를 상태로 남긴다(삭제하지 않음). PPT·이력·목록 필터와 일치하고 오류도 사라진다. 삭제가 의도라면 필터·건수 표시와 리다이렉트를 그에 맞게 정리한다.
- **테스트 공백**: `OrderFlowTests`는 "완료 후 취소 불가"만 검증하고, 확정/진행 → 취소는 검증하지 않는다. 고칠 때 이 흐름의 테스트를 먼저 추가한다.

### 6-2. 생산 물량 배분
PPT는 "주문 수량에 맞춰 4개국 공장에 생산 물량을 배분한다(일일 최대 생산량·생산원가·재고 상한 고려)"고 설명한다. 현재 앱은 배분을 담당자가 입력하고 시스템은 경로만 계산한다. 자동 배분(추천)을 이 앱의 범위로 볼지 정해야 한다. (PRD FR-14)

### 6-3. 로그인
단일 하드코딩 계정을 유지할지, 과제의 "Gate" 유형(보안 취약점 개선 제안)에서 다룰지 정해야 한다.
