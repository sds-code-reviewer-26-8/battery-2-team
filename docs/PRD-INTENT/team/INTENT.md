# INTENT — 왜 이렇게 만들었나, 무엇을 지켜야 하나 (팀 통합본)

> PRD.md가 "무엇을 해야 하나"라면 이 문서는 "왜 그렇게 되어 있나"와 "바꿀 때 무엇을 지켜야 하나"를 적는다.
> 핵심 의도만 담았다. 의도는 현재 앱의 동작과 설명 자료에서 **짐작해서 정리한 것**이며 만든 사람에게 직접 확인한 것이 아니므로 근거를 구분해 표시한다.

- 작성: 팀 통합본 (SangwooSong, KewryByun, ctkim1005, sy9169의 개인 INTENT를 비교해 합의되는 내용만 남김)
- 작성일: 2026-10-21
- 기준: 팀이 공유한 현재 앱의 동작과 프로젝트 설명 자료
- 근거 표기

  - **[설명]** 프로젝트 설명 자료 (KewryByun이 팀 안내 자료에서 정리한 내용 포함)

## 1. 목적

**"최적 경로를 자동으로 실행"하는 것이 아니라, 담당자가 비용과 일정을 비교해 선택하도록 돕고, 선택한 결과가 나중에 바뀌지 않게 보존하는 도구.** 사람이 손으로 계산하던 "어디에 얼마를 맡기고 배를 어떻게 돌릴지"를 시스템이 대신 계산하되, 최종 결정은 담당자가 한다. [설명]·[추정]

- 근거: 정답 하나를 내놓지 않고 기준이 다른 3가지 안을 나란히 보여 준다. 선택과 확정은 사람이 직접 한다. [현재 앱]

## 3. 성공 기준

- 담당자가 수량 입력부터 안 선택, 확정까지 막힘 없이 끝낼 수 있다.
- 세 안의 총 소요일과 총 비용이 한눈에 비교된다.
- 확정된 주문은 언제든 다시 열어 같은 계획과 지도 애니메이션으로 볼 수 있다.
- 기준값이 바뀐 뒤에는 오래된 시뮬레이션으로 확정되지 않는다.

## 4. 바꿀 때 지킬 방향

| ID | 방향 |
| --- | --- |
| G1 | **확정된 주문의 내용은 어떤 경우에도 바뀌지 않게 한다.** 기준값이나 계산 규칙이 바뀌어도 과거 주문을 다시 계산해 덮어쓰지 않는다. 납기·공장 운영비 같은 새 항목을 더할 때도 이미 확정된 기존 주문이 계속 정상으로 보여야 한다. (I4) |
| G2 | 주문을 확정할 때는 **항상 시스템이 다시 계산**한다. 화면에서 넘어온 계산 결과를 믿는 방식으로 바꾸지 않는다. (I3) |
| G3 | 기준값이 바뀌면 그 전에 본 시뮬레이션으로는 **확정할 수 없다.** 기준값을 바꾸는 기능을 새로 만들어도 마찬가지다. (I5) |
| G4 | 주문 상태는 **정해진 순서로만** 바뀌고, 바뀔 때마다 **이력을 남긴다.** 동시에 바꾸면 먼저 한 사람이 우선이다. 이런 보호가 필요한 새 기능에는 같은 방식을 적용한다. (I6) |
| G5 | 사용자가 보는 숫자와 저장되는 숫자는 **같은 계산에서** 나와야 한다. 단위(K, 억 원, 일, 0일차 기준)를 임의로 바꾸지 않는다. (I1, I3) |
| G6 | 계산 규칙을 바꾸면 **PRD §5와 예시 숫자를 먼저 고치고** 결과를 다시 확인한다. 특히 "한국 대기 무료"와 "운항비는 실제 항해 일수만 센다"는 정의가 바뀌면 세 안 모두의 결과가 달라진다. "운항비 최소"와 "가장 빠르게"가 비길 때의 우선순위도 유지한다. (I7) |
| G7 | 잘못된 입력은 **이유와 함께** 알리고, 일부만 저장되는 일이 없게 한다. 뜻밖의 상황(없는 주문 등)도 오류 화면이 아니라 안내 메시지로 알린다. (I9) |
| G8 | 새 기능도 **로그인한 사람만** 쓸 수 있어야 한다. 로그인 화면과 **회원가입 화면·API**만 예외이며, 가입은 가입 코드를 아는 사람만 할 수 있다. |

## 6. 의도적으로 하지 않은 것 (현재 범위 밖)

- **역할별 권한과 계정 관리:** 처음에는 소수 인원이 쓰는 내부 도구라 단일 계정으로 충분하다고 본 것으로 보인다. [추정] 이후 **회원가입(가입 코드 방식)을 도입**했다. 담당자·관리자 역할 구분, 비밀번호 변경·재설정, 계정 잠금은 여전히 범위 밖이다.
- **확정 후 주문 수정:** 근거를 보존하는 것이 목적이라 수정은 두지 않았다. [추정]
- **외부 시스템 연동:** 먼저 계산 결과를 믿을 수 있게 하는 것이 우선이다. [추정]
- **선박 적재량 제한:** 설명 자료가 "적재량은 충분하다"고 가정한다. [설명]
- **생산 물량 자동 배분, 고객사·납기, 공장 운영비:** 설명 자료에 있으나 현재 앱에는 없다. 담당자가 입력한 배분 수량을 그대로 계산한다. [설명]·[현재 앱]

## 7. 결정이 필요한 점 (미결)

1. **[(b)로 구현됨 — PR #28 병합으로 확정] 취소한 주문을 남길 것인가?**
   - 설명 자료는 취소를 하나의 상태로 본다. 이전 앱은 취소하면 주문을 지우고 변경 이력만 남겨서, 목록의 "취소" 버튼이 항상 0건이었고 취소 직후 "주문을 찾을 수 없습니다" 오류 화면이 나왔다(KewryByun이 직접 실행해 확인).
   - 선택지는 (a) 지우는 방식을 유지하고 "취소" 버튼을 없앤다, (b) 주문은 남기고 상태만 "취소"로 바꾼다였고, **(b)로 구현했다**(PR #28). 설명 자료·이력·목록 버튼과 모두 맞고 오류도 사라진다. 지금은 취소해도 주문이 남고, "취소"는 더 바꿀 수 없는 최종 상태이며, 상세·이력을 계속 볼 수 있다.
   - 남은 확인 사항: 목록의 "전체" 건수에 취소 주문을 포함하는 것이 맞는지(현재는 모든 상태의 합), 취소 주문을 언제까지 보관하고 어떻게 정리할지.
2. **[미결] 생산 물량을 시스템이 배분할 것인가?** 설명 자료는 시스템이 배분하고, 현재는 담당자가 입력한다. 자동 배분이 들어오면 수량 입력 방식이 바뀐다.
3. **[미결] 공장 운영비를 어떻게 반영할 것인가?** 하루 단위인지, 주문 건당인지, 월 고정인지에 따라 최적 경로와 3가지 안의 비교 결과가 달라진다.
4. **[미결] 고객사·납기를 어떻게 쓸 것인가?** 입력만 받을지, 납기를 넘기는 경로를 걸러 주거나 경고할지. 새로 더하는 항목은 기존 주문에 영향을 주지 않아야 한다(G1).
5. **[미결] "완료"의 기준.** 관리자가 직접 바꾸게 둘지, 배가 한국에 도착하는 일정과 연결할지.
6. **[일부 구현] 로그인과 권한.** 회원가입은 가입 코드 방식으로 구현했다. 남은 질문: 담당자와 관리자 역할을 나눌지(설명 자료는 "관리자가 상태를 변경"한다고 한다), 코드 대신 관리자 승인이 필요한지, 가입한 계정을 관리(변경·삭제)할 수단이 필요한지.
7. **[미결] 생산원가 허용 범위.** 설명 자료는 500~1,000원 수준이고 기본값 중 인도네시아는 450원이다. 입력 제한을 둘지.
8. **[미결] 확정 후 수정이 필요할 때.** 현재는 불가하다. 수정 요구가 생기면 G1과 충돌하므로 "새 주문으로 대체"할지 "취소 후 재확정"할지 정해야 한다.

## 8. 이 문서에서 [추정]인 것 (팀 확인 요청)

## 9. 이 문서의 근거와 한계
- 4명의 개인 INTENT에서 **공통으로 합의되는 의도**를 남겼다. 한 명만 가진 내용은 업무 의도일 때만 가져왔다(예: "한국 대기 무료" 해설, 성공 기준, 의도적으로 하지 않은 것). 만드는 방법에 관한 개발 내용은 제외했다.
- 앱을 직접 실행해 확인한 것은 KewryByun이 확인한 §7-1의 취소 직후 오류(PR #28에서 해결)뿐이다. 나머지는 앱의 동작이 정의된 내용을 읽고 정리했으므로 화면에서 보이는 모습과 다를 수 있다.
