# INTENT — 목적, 설계 의도, 변경 시 지킬 방향

## 1. 이 앱의 목적

- 최종 목적은 "최적 경로를 자동 실행"이 아니라 **담당자가 비용과 시간의 균형을 보고 선택하도록 돕는 것**이다. [추정]
  - 근거: 한 가지 정답 대신 서로 기준이 다른 3가지 안을 나란히 보여 주고, 선택은 사람이 한다. [코드]
- 계산 결과는 "확정"을 통해서만 업무 기록(주문)이 된다. 시뮬레이션은 얼마든지 돌려 볼 수 있는 가벼운 행위다. [코드]

## 2. 설계 의도

### 2.1 시뮬레이션과 확정을 분리했다
- 시뮬레이션은 저장하지 않고, 확정만 저장한다. 수량을 바꾸면 이전 결과는 화면에서 사라진다. [코드]
- 의도: 부담 없이 시험해 보게 하고, 기록(주문)에는 **본인이 선택한 결과만** 남긴다. [추정]

### 2.2 확정 시 서버가 다시 계산한다
- `BatteryService.confirm` 주석: "클라이언트 값은 믿지 않는다". [코드]
- 의도: 화면 조작이나 오래된 화면으로 **잘못된 비용·일정이 기록되는 것**을 막는다.

### 2.3 확정 주문은 확정 당시 모습으로 통째로 보관한다
- 수량, 마스터 값, 경로, 일별 생산을 JSON 스냅샷(`planJson`)으로 저장한다. [코드]
- 의도: 마스터(항해 일수·원가 등)가 나중에 바뀌어도 **과거 주문의 근거를 재현**할 수 있게 한다. 주문 상세가 저장된 계획으로 지도 애니메이션까지 그리는 것도 이 때문이다. [코드]

### 2.4 마스터 버전으로 "시뮬레이션 이후 변경"을 감지한다
- 마스터를 저장할 때마다 버전이 올라가고, 확정 시 시뮬레이션 때의 버전과 비교한다. [코드]
- 의도: 사용자가 본 숫자와 저장되는 숫자가 **다르게 되는 일을 원천 차단**한다.

### 2.5 동시 수정은 "나중에 누른 쪽을 거부"한다
- 주문에 낙관적 락 버전이 있고, 화면이 본 버전과 다르면 거부한다. [코드]
- 의도: 잠금으로 막기보다, 충돌을 알리고 **새로 고침 후 재시도**하게 하는 가벼운 방식을 택했다. [추정]

### 2.6 상태 규칙은 한 곳(`OrderStatus`)에 둔다
- 허용되는 다음 상태 목록을 enum이 가지고, 화면 버튼도 서버 검증도 이를 쓴다. [코드]
- 의도: 규칙이 화면과 서버에 **따로 존재해 어긋나는 일**을 막는다. [추정]

### 2.7 계산에는 "자기 검산"이 있다
- 일별 생산을 다시 돌려 수거량과 재고가 다르면 예외로 중단한다. [코드]
- 의도: 경로 탐색 로직이 복잡하므로, **틀린 계획을 조용히 내보내느니 실패하는 쪽**을 택했다. [추정]

### 2.8 경로는 "모든 경우를 탐색"한다
- 나라를 배에 나누는 모든 방법 × 왕복 패턴 × 방문 순서를 전부 비교한다. [코드]
- 의도: 공장이 4곳으로 적다는 전제에서 **휴리스틱 없이 최적을 보장**한다. [추정]
- 대가: 나라 수가 늘면 계산량이 급격히 늘어난다(→ 4절).

### 2.9 "가까운 곳부터" 안은 의도적으로 단순하다
- 탐색 없이 가까운 순으로 배에 돌아가며 배정한다. [코드]
- 의도: 최적화 결과와 비교할 **기준선** 역할. [추정]

### 2.10 기준 정보는 코드가 아니라 화면에서 고친다
- 공장·항로·배 정보는 DB에 두고 마스터 화면으로 수정한다. 처음 기동 시 비어 있으면 초기값을 넣는다. [코드]
- 의도: 현업이 운영 중 값을 바꿀 수 있게 하고, 코드 수정·배포 없이 **계산 조건을 바꾸게** 한다. [추정]

### 2.11 단순한 기술 선택
- 서버 렌더링(Thymeleaf) + 필요한 곳만 바닐라 JS, 파일 기반 H2 DB. 테스트는 인메모리 H2. [코드]
- 의도: 소규모 내부 도구로서 **빌드·배포·운영 부담을 최소화**. [추정]

## 3. 변경 시 지켜야 할 방향

| # | 방향 | 이유 |
|---|---|---|
| G1 | **확정된 주문의 내용은 어떤 경우에도 바뀌지 않게 한다.** 마스터·계산 규칙이 바뀌어도 과거 주문을 다시 계산해 덮어쓰지 않는다. | 과거 주문의 근거 보존(2.3) |
| G2 | 확정은 **항상 서버 재계산**을 거친다. 성능을 이유로 화면 값을 받아 저장하지 않는다. | 2.2 |
| G3 | 마스터를 바꾸는 모든 경로는 **버전을 올린다.** | 2.4 |
| G4 | 계산 규칙(생산·수거·비용·출항 시점)을 바꾸면 **PRD 4절을 먼저 고치고**, 계산 단위 테스트(`PlannerTest`)와 자기 검산이 함께 통과해야 한다. | 규칙이 곧 제품이다 |
| G5 | 상태 전이 규칙은 `OrderStatus` 한 곳에서만 정의한다. 화면에 규칙을 복제하지 않는다. | 2.6 |
| G6 | 사용자가 보는 숫자와 저장되는 숫자는 **같은 계산에서** 나와야 한다. 표시용 계산과 저장용 계산을 따로 만들지 않는다. | 신뢰 |
| G7 | 단위(K, 억 원, 일, 0일차 기준)를 임의로 바꾸지 않는다. 바꿀 때는 화면·저장 JSON·문서를 함께 고친다. | 혼동 방지 |
| G8 | 오류는 **이유와 함께** 알린다(입력 오류, 충돌, 마스터 변경). 이유 없는 실패를 만들지 않는다. | 사용성 |
| G9 | 접근 통제는 한 곳(요청 인터셉터)에서 일괄 적용한다. 화면마다 따로 막지 않는다. | 누락 방지 |

## 4. 알려진 제약과 트레이드오프

- **계산량:** 전수 탐색이라 공장(나라)이 늘면 느려진다. 나라를 추가하려면 먼저 탐색 방식(가지치기·휴리스틱)을 재검토한다. [코드 기반 추정]
- **총 수량 상한 100,000K:** 입력 폭주를 막는 안전 장치로 보인다. [추정]
- **배 최대 4척:** 서비스에 상수로 고정되어 있다. 늘리려면 계산량도 함께 본다. [코드]
- **운항비 정의:** 운항비는 "실제 항해 일수"만 센다. 한국에서 기다리는 시간은 비용에 들어가지 않는다. 이 정의가 바뀌면 "운항비 최소" 안의 결과가 달라진다. [코드]
- **단일 공용 계정:** 로그인은 하나의 고정 계정이며, 작성자·변경자는 모두 같은 값으로 남는다. [코드]

## 5. 미결 사항 (확정되지 않은 요구사항)

1. **[미결] 취소한 주문을 남길 것인가?** 현재는 상태를 "취소"로 바꾸면 주문이 **삭제**되고 이력만 남는다(`changeStatus`). 그런데 목록에는 "취소" 필터가 있어 어긋난다. 결정이 나면 PRD 5절을 갱신한다.
   - 남긴다면: 삭제 대신 상태만 변경, 목록·상세에서 조회 가능.
   - 삭제가 의도라면: "취소" 필터 제거, 이력이 가리킬 주문이 없다는 점 정리.
2. **[미결] 로그인 방식:** 고정 계정(admin)을 임시로 쓰는 것인지, 사용자 구분이 필요한 것인지. 사용자가 구분돼야 하면 PRD의 "작성자·변경자 이력"이 의미를 갖는다.
3. **[미결] 확정 후 수정:** 현재는 불가(PRD 9절). 수정 요구가 생기면 G1과 충돌하므로 "새 주문으로 대체" 방식을 우선 검토한다.
