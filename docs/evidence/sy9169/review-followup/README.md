## 2. 달라진 점 (동작이 바뀌는 것)
1. **없는 주문을 요청하면 API 가 404 를 돌려줍니다**(이전 400). 화면은 정적 파일이라 항상 200 으로 열리고 "주문을 찾을 수 없습니다" 안내를 보여 주므로, "없음"을 상태 코드로 구분할 수 있는 곳은 API 뿐입니다. 이후 React 같은 화면에서 이 API 를 쓸 때 400(입력 오류)과 404(없음)를 구분할 수 있습니다.
2. **로그인할 때 세션 ID(`JSESSIONID`)가 바뀝니다.** 로그인 화면을 열 때 받은 세션 ID 와 로그인 후의 ID 가 다릅니다. 사용자가 보는 동작은 같습니다.
3. **깨진 요청 등 프레임워크가 만드는 오류 응답에서 `trace`와 `message`가 빠집니다.** 업무 오류(입력 검증, 충돌 등)는 `ApiExceptionHandler` 가 따로 응답하므로 그대로입니다.
4. **마스터 화면의 `저장` 버튼이 값을 불러오기 전에는 꺼져 있습니다.** 전에는 입력칸이 그려지기 전에 누르면 빈 값이 서버로 전송되어 24개 오류가 나왔습니다.
5. 로그인 화면은 서버에 연결할 수 없을 때, 마스터 화면은 저장 후 재조회가 실패했을 때 각각 알맞은 안내를 보여 줍니다.

|---|---|---|---|

## 3. 발견한 문제와 원인 (반영하는 과정에서)
1. **설정 이름이 Spring Boot 4 에서 바뀌어 있었습니다.** 처음에 `server.error.include-stacktrace=never` 를 넣었는데 `trace` 가 그대로 나왔습니다(같은 값을 실행 인자로 넘겨도 마찬가지). Spring Boot 4.1.1 의 설정 메타데이터를 확인하니 오류 응답 설정이 `spring.web.error.*` 로 옮겨져 있었고, 이 이름으로 바꾸자 해결되었습니다. 설정 파일에 그 사실을 주석으로 남겼습니다.
2. **주문 행을 글자로 찾던 테스트가 취소 주문이 쌓이자 실패했습니다.** `hasText: '#42'` 는 `#142` 도 찾습니다. 취소해도 주문이 지워지지 않으면서(PR #28) 같은 서버에 3번 실행하자 번호가 100을 넘어 No.22 가 한 번 실패했습니다(아래 표 C3). 처음에는 정규식으로 정확히 찾으려 했으나, 화면의 행은 셀 사이에 공백이 없어 `#4` 와 날짜가 붙은 글자(`#42026-…`)가 되어 오히려 여러 테스트가 실패했습니다(기록 생략: 중간 시도). 결국 **그 주문으로 가는 링크(`a[href="/orders/{id}"]`)가 든 행**을 찾도록 바꿨고, 같은 서버에서 4번 연속 실행해도 통과합니다(D1~D4).
3. **두 탭 테스트(T25)는 화면이 데이터를 받은 뒤 그려지는 구조에서 이론적으로 순서가 어긋날 수 있습니다.** 탭 B 의 화면이 탭 A 가 상태를 바꾼 **뒤에** 데이터를 받으면, 탭 B 는 이미 '진행' 상태를 받아 충돌이 나지 않습니다. 탭 B 의 버튼이 그려진 것을 확인한 뒤 탭 A 가 바꾸도록 대기를 추가했습니다. (@KewryByun 님이 겪은 1회 시간 초과의 원인으로 추정하지만 그 한 번을 재현하지는 못했습니다.)
4. **마스터 화면의 `저장` 버튼은 HTML 에 고정되어 있어**, 입력칸이 그려지기 전에 누르면 빈 값이 전송될 수 있었습니다(저장 버튼을 화면을 연 직후 바로 누르는 E2E 2개가 이 순서에 기대고 있었음). 값을 불러온 뒤에 켜도록 바꿔, 테스트는 버튼이 켜질 때까지 자동으로 기다립니다.
