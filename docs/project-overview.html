1. 무엇을 하는 시스템인가

DSD는 한국 본사에서 배터리 셀(전기차용 2170 원통형)을 생산·공급하는 회사입니다. 중국·일본·베트남·인도네시아에 공장이 있고, 완성된 셀은 배로 한국까지 실어 옵니다.

이 프로그램은 고객 주문이 들어왔을 때, "어느 배가 어느 공장을 어떤 순서로 돌아야 비용이 적거나 빨리 끝나는지"를 미리 계산해 보여 주고, 마음에 드는 방법을 골라 주문으로 확정하게 합니다.

공장 4곳하루 생산량, 창고(재고) 용량, 셀당 원가가 나라마다 다릅니다.
배 1~4척빌려 쓰며 척당 하루 약 1억 원. 한국 항구에서 대기하는 동안은 무료입니다.
단위 K1K = 셀 1,000개. 예: 주문 15,000K ≈ 1,500만 개.

2. 업무 흐름

1주문 추가공장별 수량을 입력합니다. 슬라이더를 움직이면 합계가 유지되도록 이웃 나라가 자동 조정됩니다.
2시뮬레이션경로 3가지(운항비 최소 / 가장 빠르게 / 가까운 곳부터)와 비용·일수, 지도 애니메이션을 보여 줍니다.
3주문 확정경로 하나와 메모를 골라 확정합니다. 이 순간의 계획이 그대로 저장됩니다.
4상태 관리주문 목록에서 상태를 바꾸고 이력을 확인합니다.

화면은 5개입니다: /login /orders(목록) /orders/new(추가) /orders/{id}(상세) /master(기준값).

4. 계산 규칙 (Planner)

  1. 0일차에 모든 공장이 동시에 생산을 시작합니다.
  2. 하루 생산 = 하루 최대, 남은 창고 공간, 남은 주문량 중 가장 작은 값.
  3. 창고가 차면 배가 가져가기 전까지 생산이 멈춥니다.
  4. 배는 도착하면 그 시점의 재고를 전부 싣고 갑니다.
  5. 한 나라는 한 척의 배만 방문합니다.
  6. 필요 방문 횟수 = 올림(주문량 ÷ 재고 상한). 여러 번이면 한국에 들러 내려놓고 다시 출항합니다.
  7. 배는 재고가 찰 날에 맞춰 늦게 출항합니다 (한국에서 기다리는 건 무료).

예시로 이해하기 (PlannerTest의 값)

베트남 2,000K, 하루 200K

생산 10일 · 한국↔베트남 5일
→ 5일차 출항, 10일차 도착, 15일차 귀환
운항비 = 10일 × 1억 = 10억 원

일본 4,500K, 재고 상한 2,000K

방문 3번 = 2,000 / 2,000 / 500
배는 한국을 3번 왕복합니다.

경로 3종

코드이름기준
COST운항비 최소모든 후보 중 운항비가 가장 적은 것 (같으면 더 빠른 것)
FAST가장 빠르게모든 후보 중 총 일수가 가장 짧은 것 (같으면 더 싼 것)
NEAR가까운 곳부터한국에서 가까운 나라부터 배에 번갈아 배정 (단순 규칙, 최적 아님)
비용 = 생산 원가(주문 K × 1,000 × 셀당 원가) + 운항비(배가 항해한 일수 × 일 운항비). 한국 대기일은 포함되지 않습니다.

6. 주문 확정은 어떻게 안전하게 이뤄지나

왜 이렇게? 화면에서 본 결과와 저장되는 결과가 어긋나지 않게 하기 위해서입니다. 확정 후에는 계획 전체(마스터 값 포함)가 주문에 저장되므로, 나중에 기준값을 바꿔도 이미 확정된 주문은 달라지지 않습니다.

7. 주문 상태 변경

  • 업무 의미: 확정=구두 확정, 진행=계약서 작성 후 생산 시작, 완료=물량이 한국에 모두 입고, 취소=확정/진행 중 취소.
  • 화면의 version과 현재 값이 다르면(그 사이 다른 사람이 변경) 409 충돌로 거절합니다. DB 낙관적 락(@Version)이 한 번 더 막습니다.
  • 모든 변경은 OrderStatusHistory에 기록됩니다.
  • 현재 구현 취소하면 주문 행이 삭제되고 이력만 남습니다.

9. 코드 리뷰 체크 포인트

  • 확정 로직에서 클라이언트가 보낸 계획을 신뢰하는 코드가 생기지 않았는가 (서버 재계산 원칙)
  • 마스터를 바꾸는 코드가 masterVersion을 올리는가
  • 상태를 바꿀 때 이력을 남기고 version을 비교하는가
  • 새 URL이 로그인 검사(LoginInterceptor) 대상인가 / API 오류가 {error, conflict} 형태인가
  • simulation 패키지에 Spring·JPA 의존이 들어오지 않았는가
  • Plan/StoredPlan 필드를 바꿨다면 planview.js, anim.js, 이미 저장된 주문과 호환되는가
  • 계산 규칙을 바꿨다면 PlannerTest의 구체적 숫자 테스트가 함께 바뀌었는가
  • 컨트롤러에 비즈니스 로직이 새로 들어오지 않았는가
조심해서 볼 파일 Planner.java(완전 탐색·일정 계산), BatteryService.java(동시성·검증), AppController.java(화면+API 혼재), anim.js(고정 지도 좌표). Planner는 공장·배가 늘면 후보 수가 급격히 늘어나는 구조입니다.
