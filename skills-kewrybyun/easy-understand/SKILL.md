# easy-understand — 비개발자용 프로젝트 이해 HTML 만들기

프로젝트 코드를 읽고, **개발 용어 없이** 업무(요구사항) 관점으로 설명하는 HTML 2개를 만든다.

| 산출물 | 파일 | 목적 |
|---|---|---|
| 이해 가이드 | `docs/understand-guide.html` | 3개 탭으로 단계별 이해 + 인터랙티브 체험 |
| 프로토타입 | `docs/understand-prototype.html` | Mock Data로 실제 앱처럼 만져 보는 단일 HTML |

기준 템플릿(이 저장소 = 배터리 주문/배송 시뮬레이션용으로 작성됨)은 `assets/` 에 있다.
- `assets/guide-template.html`
- `assets/prototype-template.html`
- `scripts/verify.js` — 두 HTML을 가상 브라우저(jsdom)에서 실제로 눌러 보는 검증 스크립트

## 절차

1. **코드 파악** — `CLAUDE.md`, 엔티티, 서비스, 계산 로직(시뮬레이션/규칙), 화면 목록을 읽는다.
   코드를 그대로 설명하지 말고 "누가 / 무엇을 / 왜 / 어떤 규칙으로" 로 번역한다.
   **상태 변경·삭제 같은 동작은 서비스 코드를 직접 읽고 확인한다.** (예: 이 저장소는 주문을 취소하면 주문이 삭제되고 기록만 남는다. 상태 enum만 보고 "취소 주문이 목록에 남는다"고 쓰지 않는다.)
2. **템플릿 복사** — 두 템플릿을 `docs/` 로 복사한다. 같은 프로젝트라면 그대로 써도 된다.
   다른 프로젝트라면 아래 "내용 교체 지침"에 따라 내용만 바꾼다. 뼈대(탭, 스타일, 스크립트 구조)는 유지한다.
   문자열 치환으로 파일을 만들 때는 `/* ... */` 같은 주석·괄호를 통째로 지우거나 닫는 부분을 빠뜨리지 않는다. (주석이 안 닫히면 그 아래 함수가 전부 사라지는데 문법 검사는 통과한다.)
3. **검증 (필수, "열어 봤다"로 대체 금지)** — 아래 "검증 방법"의 스크립트를 실행해 전부 PASS 인지 확인한다.
   스크립트 오류가 없어도 **화면에 Mock 데이터가 실제로 보이는지**가 핵심이다. 계산 함수만 따로 돌려 보고 끝내지 않는다.
4. 사용자에게 파일 경로와 "단순화한 부분", 검증 결과(통과 항목 수)를 알려 준다. 브라우저에서 직접 눌러 보지 못했다면 그렇다고 말한다.

## 검증 방법

jsdom 은 **임시 폴더**에 설치한다. 프로젝트나 홈 폴더(`~`)에서 `npm i` 하지 않는다. (홈에 이미 `package.json` 이 있으면 의존성이 섞인다.)
Node 20 계열은 최신 jsdom 과 맞지 않으므로 `jsdom@24` 를 쓴다.

```
mkdir <임시폴더> && cd <임시폴더> && npm init -y && npm i jsdom@24
node <스킬폴더>/scripts/verify.js <프로젝트>/docs/understand-guide.html <프로젝트>/docs/understand-prototype.html
```

(`verify.js` 는 현재 폴더에서 jsdom 을 찾는다. 반드시 jsdom 을 설치한 폴더에서 실행한다.)

확인 항목: 스크립트 오류 없음 · 흐름도/슬라이더/상태 버튼 동작 · **Mock 주문이 목록에 2건 이상 표시** · 목록·카드에 `NaN`/`undefined` 없음 ·
계획 3가지 표시 · 확정 → 상태 변경 → 취소 시 삭제 · 총량 상한 검사 · 기준 정보 저장.
화면 id/버튼 문구를 바꿨다면 `verify.js` 의 선택자도 함께 맞춘다.

## 가이드 HTML 규칙 (3개 탭)

- **개발 지식 없이 이해되는 내용만.** 클래스/DB/API/프레임워크 같은 단어 금지. 필요하면 일상어로 풀어 쓴다.
- 탭은 이해 순서대로 3개:
  1. **무엇을 하는 시스템인가요?** — 누가 쓰고, 어떤 문제를 풀고, 큰 흐름은 무엇인지. (클릭하면 설명이 바뀌는 흐름도)
  2. **어떤 규칙으로 계산하나요?** — 핵심 업무 규칙. 입력값을 바꾸면 결과가 바뀌는 **슬라이더/버튼 체험** 필수.
  3. **일이 어떻게 진행·관리되나요?** — 상태 변화(생명주기), 허용/불허 전환, 담당자가 할 수 있는 일. (버튼으로 상태 전환 체험)
- 각 탭 끝에 "한 줄 요약" 박스. 단계 이동 버튼(이전/다음)과 키보드 ←/→ 지원.
- 단일 파일(HTML+CSS+JS 인라인), 외부 라이브러리 없음, 모바일 폭에서도 깨지지 않게.
- 다크모드 대응(`prefers-color-scheme`), 색만으로 정보를 구분하지 않는다(텍스트/아이콘 병기).

## 프로토타입 HTML 규칙

- **Mock Data 는 화면을 열자마자 보여야 한다.** 코드의 초기값(기본 마스터 데이터)을 따르고, 가짜 주문 2건 이상을 미리 넣는다(서로 다른 상태로).
- **파생 수치(일수·비용 등)는 손으로 적지 않는다.** 가짜 주문은 프로토타입의 계산 함수(`plan()`)로 만들어 화면의 다른 값과 어긋나지 않게 한다 (`mkOrder`).
- 비용은 코드의 정의대로 표시한다. (이 저장소: 총 비용 = 생산비 + 운항비, 금액 단위는 억 원)
- 실제 앱의 핵심 화면 흐름을 한 파일에서 재현한다: 주문 목록 → 새 주문(시뮬레이션) → 확정 → 상태 변경 → 기준 데이터 수정.
- 코드에 있는 입력 제한(예: 총 수량 상한, 배 척수 범위)도 같이 검사한다.
- **서버/DB 없음.** 상태는 메모리(새로고침 시 초기화)로만 유지한다.
- 계산은 실제 로직을 **단순화**한 것임을 화면에 명시한다(결과가 실제 앱과 다를 수 있음).

## 내용 교체 지침 (다른 프로젝트에 적용할 때)

- 가이드: 탭 제목·문구, 흐름도 단계(`FLOW`), 체험 규칙(`slider`), 상태 목록(`STATES`)만 바꾼다.
- 프로토타입: `MASTER`(기준 데이터), `plan()`(단순화 계산), `mkOrder(...)` 로 만드는 `orders` 초기값, 화면 라벨만 바꾼다.
- 실제 코드에 없는 기능을 만들어 넣지 않는다. 모르면 "확인 필요"로 표시한다.
