# code-explainer-html

처음 보는 코드를 **적은 에너지로 단계별로 이해**하고 이후 **코드 리뷰**를 편하게 하기 위한 설명 HTML을 만든다.
결과물은 서버나 빌드 없이 브라우저로 바로 열리는 **단일 HTML 파일**이다.

## 대상 독자 가정
- 이 코드를 처음 본다. 이해에 쓸 수 있는 에너지가 적다.
- 개발 용어보다 **업무 의미(무엇을 위한 코드인가)**를 먼저 알고 싶다.
- 나중에 PR을 리뷰해야 한다. 그래서 "무엇을 확인해야 하는지"가 필요하다.

## 진행 순서

1. **범위 확인**: 대상(프로젝트 전체 / 디렉터리 / 파일 / PR)과 저장 위치를 확인한다. 불명확하면 한 번만 묻는다. 기본 저장 위치는 `docs/<대상>-overview.html`.
2. **재료 수집** (필요한 만큼만 읽는다)
   - `.ua/knowledge-graph.json`(또는 `.understand-anything/`)이 있고 최신이면 구조·계층·투어를 먼저 활용한다.
     최신 여부: 그래프의 `project.gitCommitHash`와 `git rev-parse HEAD`를 비교하고, 프로젝트 범위의 변경(`git diff --name-only <hash> HEAD -- .`)이 없는지 본다. 오래됐으면 사용자에게 `/understand` 재실행을 권한다.
   - 그래프 요약은 **방향을 잡는 용도**로만 쓰고, 설명에 넣는 사실은 **실제 소스에서 다시 확인**한다 (요약이 추정일 수 있다).
   - 진입점 → 서비스/도메인 로직 → 데이터 → 화면 → 테스트 순으로 읽는다. 테스트는 규칙의 가장 짧은 설명서다.
3. **내용 구성**: 아래 "섹션 구성"에 맞춰 정리한다.
4. **HTML 작성**: 이 스킬 폴더의 `template.html`을 복사해서 시작한다(스타일, 다크 모드, 목차, 테마 버튼 포함). 플레이스홀더(`{{...}}`)를 모두 채우거나 지운다.
5. **자체 점검** (아래 체크리스트) 후 저장한다.
6. 저장 경로와 "먼저 어느 섹션부터 보면 되는지"를 한두 줄로 알려 준다.

## 섹션 구성 (대상에 맞게 필요한 것만)

| 순서 | 섹션 | 담을 것 |
| --- | --- | --- |
| 1 | 무엇을 하는 코드인가 | 업무/목적 중심 설명. 개발 용어 최소화 |
| 2 | 업무(사용자) 흐름 | 단계 카드 3~5개 |
| 3 | 핵심 용어 | 표: 용어 / 뜻 / 코드에서의 이름 |
| 4 | 핵심 규칙 | 번호 목록 + **숫자 예시**(테스트에서 가져온 값이면 최고) |
| 5 | 코드 구조 | 계층 그림(인라인 SVG) + 패키지 역할 표 |
| 6 | 핵심 흐름 1~2개 | 가장 중요한 요청/처리 순서를 그림이나 단계로 |
| 7 | 상태·규칙 변화 | 상태가 있다면 전이 그림 |
| 8 | 알아둘 점 | 의도가 불분명한 동작, 설명 문서와 다른 점 (`.tag.warn`) |
| 9 | 리뷰 체크 포인트 | `ul.check` 체크리스트: 이 코드를 바꾸는 PR에서 무엇을 볼지 |
| 10 | 파일 맵 | `details`로 접어서 계층별 파일 역할 |

PR/변경분이 대상이면 위 대신: **변경 요약(업무 언어) → 영향받는 흐름 → 확인할 위치 → 리뷰 체크리스트** 순으로 구성한다.

## 작성 원칙
- **사실만 쓴다.** 코드·테스트에서 확인한 것만 단정한다. 추정은 "추정"이라고 표시하고, 모르면 비워 둔다.
- **업무 언어 먼저, 코드 이름은 옆에** `<code>`로 붙인다.
- 한 섹션은 한 화면 분량. 길면 `details`로 접는다.
- 그림은 **실제 구조/흐름**을 보여 줄 때만 쓴다(인라인 SVG, 템플릿의 클래스 사용). 장식용 그림은 넣지 않는다.
- 숫자 예시는 테스트나 기본값에서 가져온다. 새로 지어내지 않는다.
- 의심스러운 동작(예: 데이터가 삭제됨, 하드코딩된 계정)은 비판하지 말고 **"알아둘 점"**으로 중립적으로 적는다.
- 한국어로 쓴다(사용자가 다른 언어를 요청하면 그에 따른다).

## HTML 규칙
- 단일 파일. 외부 CDN·폰트·이미지 **금지**(오프라인·사내망에서 열려야 한다). CSS/JS는 인라인.
- 색은 `:root` 변수만 사용하고 라이트/다크를 모두 지원한다(`template.html`이 이미 구현).
- 모바일 폭에서도 가로 스크롤이 생기지 않게 한다(표는 짧게, SVG는 `viewBox`).
- `<title>`은 2~4단어 이름.
- 사내 코드 설명이므로 **외부에 게시하지 않는다**(claude.ai Artifact 등으로 올리려면 사용자 확인을 먼저 받는다).

## 자체 점검 체크리스트
- [ ] 모든 `{{...}}`가 채워지거나 삭제됐다
- [ ] 코드 이름(클래스·메서드·경로)을 실제 파일에서 확인했다
- [ ] 숫자·규칙은 소스나 테스트에 근거가 있다
- [ ] 추정과 사실이 구분돼 있다
- [ ] 리뷰 체크 포인트가 "이 코드의 실제 위험 지점"을 가리킨다 (일반론 금지)
- [ ] 외부 리소스 참조가 없다
- [ ] 브라우저에서 열어 목차 이동과 테마 전환이 되는지 확인했다(가능한 경우)

## 이 스킬이 하지 않는 것
- 코드를 수정하거나 리팩터링 제안을 하지 않는다(설명 자료만 만든다).
- 보안·버그 리뷰를 대신하지 않는다. 그건 `/code-review`를 쓴다.
